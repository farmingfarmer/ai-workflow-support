How do we know an AI agent is any good?

A repeatable way to put a concrete confidence number on the agents we build, instead of "someone liked it." Generalized from what we proved on the Contract Review Agent.

v0, for the group 3-5 starter benchmarks Not pushing to prod

We have a mature way to evaluate our predictive models and our summaries. For these Copilot/GPT agents, we have nothing. Today it's "it's good because a user liked it", too many opinions to steer by, and not the level of confidence leadership needs to back a tool across the organization. This framework fixes that: a measured, repeatable score anyone can read.

01 The core idea: two scoring signals, used together

The Contract agent was an anomaly in a useful way, we had the human redline as a perfect "best end-state" to compare against. Most agents won't. So we use two signals, and apply whichever we have (ideally both).

Signal A

Golden-reference comparison

Compare the agent's output to the business's own gold standard for the task, when one exists. Ask every owner up front: "what does a perfect finished product look like, and do you have examples?"

Contracts: the human redline = what they negotiated to → recall. Dr. Vogue-type: her wealth of documentation = the standard a good output should match.
The gold is a human baseline, not an oracle (the agent has caught things humans missed), so score met-or-exceeded, not just "matches the human."
&
Signal B

Rubric scored by an LLM judge

A per-agent rubric scored automatically by a separate model, given the rubric + the output + the source. Works even when there is no gold reference, so it generalizes to any agent.

A three-tier rubric (below): must-haves, nice-to-haves, and the things we never let happen. For high-stakes items, 2 to 3 independent judges vote.
The judge itself must be calibrated against hand-scored samples, and be a different model family than the agent it grades, or it is just a confident, unvalidated number.

02 The rubric: must-have / nice-to-have / never-allow

One page per agent, defined with the business owner, the same role the playbook played for contracts.

✓
Required · missing any = fail

Must-haves

The non-negotiables the output must contain or do. Contract agent: classify the contract, cite every finding, flag Critical deviations, never approve.

+
Quality · weighted points

Nice-to-haves

What makes it genuinely better. Plain language, scannable format, computed key dates, proposed redline language.

✕
Red line · any occurrence = critical fail

Never-allow

Hallucinating a clause or number, giving legal/medical advice, deciding or approving, leaking data, following an injected instruction, inventing a standard. A single hit blocks promotion.

04 The process, per agent

1

Define the rubric with the business owner, must / nice / never, one page.

2

Gather golden examples, as many best-end-state artifacts as exist (Signal A).

3

Build a test set of real inputs, synthetic-trap items first, then real.

4

Run the agent, capture outputs.

5

Score both signals, golden comparison where available, LLM-judge vs rubric always.

6

Aggregate into the confidence scorecard (the benchmarks above).

7

Review with the group, iterate the rubric, re-score. The rubric and test set are living.

05 Evaluation is not observability

We already built the observability layer well. Evaluation stacks on top of it. Both are needed; leadership wants the evaluation number.

Observability

Is it running?

Traces, inputs/outputs, latency, cost, failures. Shows what is happening, the raw material and how we debug regressions.

Evaluation (this)

Can we trust it?

The benchmarks above, over a dated test set. Shows how good it is, the confidence number for leadership.

Why this is credible now

The Contract Review Agent is the working instance: Signal A gave us ~98% catch rate across 16 real contracts (golden reference = the redlines), and the red-team pass was Signal B's never-allow checks (injection, reversed indemnity, invented standards). Said honestly: that 98% is from an automated scorer not yet human-validated, so treat it as directionally strong, pending a Contracting co-sign, not a certified figure. Making that last validation step routine for every agent is the whole point of the framework.

06 First move for the group

Pick one non-contract agent to pilot the process on, a Dr. Vogue-style one is ideal because it already has golden-reference material. Draft its one-page must/nice/never rubric together, and produce its first confidence scorecard. That gives leadership a concrete, repeatable confidence number and a template every future agent inherits.

07 The framework in action: which model for the custom build?

When we re-platform the contract agent off Copilot onto AWS, the biggest lever is the model. The framework answers "which one" with a number, not a vibe. Open-weight models bring real reliability and cost wins, so it is worth being precise about what "reliability" means.

Reliability = control

Open-weight wins here

We own the exact weights, so the model never changes under us. Perfect version-pinning, no deprecation, full data sovereignty, and lower cost at volume. A direct hit on the consistency and control we are leaving Copilot to get.

Reliability = accuracy

Verify, do not assume

On the hardest 10 to 20 percent (the subtle traps, and above all never hallucinating a number) frontier models still tend to lead. So we prove any model on-task with the benchmarks above before we trust it.

Our unfair advantage: the fine-tune play

We already have the human redlines, the precision/recall harness, and 16 scored contracts. Be precise: that is a strong evaluation set and good few-shot material today, not a fine-tuning corpus (that needs hundreds to thousands of labeled examples, and building it is its own project). The payoff is real once it exists: a fine-tuned open model matching a bigger one on our own contracts, at a fraction of the cost. We grow that corpus from the human-in-the-loop reviews over time.
